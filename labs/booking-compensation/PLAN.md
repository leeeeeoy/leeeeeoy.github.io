# Research Plan — booking-compensation

- 버전/날짜: v1 / 2026-10-23. 상태: 사용자 요청으로 로컬 구성·검증 승인.
- 승인 근거: 결제 뒤 예약 실패·보상과 트래픽 증가 시의 문제를 연구하기 위해 Go 두 서버·DB·Valkey·Slack·가상 PG를 Docker로 구성하고 동작을 확인하라는 요청.
- 기존 `concurrency-integrity` P0와 원본은 보존한다. 그 실험의 P1/P2를 소급 실행하지 않는다.
- 범위: 독립 합성 구현, Docker 기동, 작은 장애·경합·포화 확인, 원본·재현 방법·연구 기록. Push·배포·공개 글은 포함하지 않는다.
- 방식: [Failure-Driven Experiment](../../docs/guides/14-engineering-lab-workflow.md). 이번에는 문제를 관측하는 기준 구현까지 만들며 자동 복구 해법을 한꺼번에 도입하지 않는다.

## 질문과 배경

사용자의 질문: 결제는 성공했으나 예약이 실패할 때 어떻게 보상해야 할까? 트래픽이 늘면 주요 실행·실패 처리 단계에서 무엇이 병목이 될까?

회사에서 경험한 문제와 비슷한 상황을 독립 합성 모델로 재현한다. 구체적인 내부 코드·스키마·업무 정책·식별자·데이터는 사용하지 않는다. 앱은 PG 승인 후 예약을 요청한다. 예약 서버는 별도 일정 서버를 호출하고 자신의 DB에 결과를 저장한다. 두 DB의 원자적 커밋은 없다.

## 가설 — 실행 전

1. 일정 서버의 성공 뒤 로컬 저장이 실패하면 일정 삭제를 보상해도 PG 승인은 자동으로 사라지지 않을 것이다.
2. 일정 커밋 뒤 응답이 유실되면 호출자는 일정 ID와 실제 성공 여부를 알 수 없을 것이다. timeout을 확정 실패로 처리해 무조건 환불하는 것은 안전하지 않다.
3. 보상 HTTP 호출도 실패할 수 있다. 로그·Slack만 남기는 구현은 최종 상태를 스스로 수렴시키지 못할 것이다.
4. DB 연결을 잡고 외부 호출을 기다리면 작은 풀에서도 독립 DB 조회가 밀릴 것이다. 동기 Slack 발송은 커밋 이후에도 응답을 늦추며 burst에서 알림을 유실할 수 있다.

## 구성·불변 조건

- `orchestrator` + 전용 PostgreSQL: 승인 조회, Valkey의 짧은 payment별 lease, DB 트랜잭션, 일정 생성 HTTP, 로컬 예약 저장, best-effort 일정 삭제, 동기 Slack.
- `scheduler` + 별도 PostgreSQL: 자원별 advisory lock·구간 겹침 검사·생성/취소. 같은 자원 활성 구간 `[start,end)`은 겹치지 않는 합성 계약이다.
- `pg`: 가상 승인 조회·멱등 환불 스텁. 메모리 저장이며 PG 프로세스 재시작 내구성을 검증하지 않는다.
- `slack`: 지연·고정 window 한도·429와 수락/거절 카운터를 제공하는 로컬 스텁. 실제 Slack의 한도 모델이라고 주장하지 않는다.
- Valkey: 임시 lease만 담당한다. 영구 멱등성·환불 큐·장애 복구의 원장으로 간주하지 않는다.

핵심 판정은 독립 DB 연결과 PG/Slack 조회로 한다. HTTP 성공만으로 판정하지 않는다. 정상 완료에는 로컬 예약과 일정이 각각 하나, PG는 CAPTURED이어야 한다. 실패 시 결제·각 DB에 무엇이 남았는지 구분하고, 환불도 성공 예약에 대한 오환불과 중복 효과가 없어야 한다. 기준 구현에서 조건이 깨지는 사례는 **예상한 문제의 재현**이지 올바른 복구의 통과가 아니다.

## 최소 확인 순서

| 단위 | 개입·실행 | 확인할 증거 |
|---|---|---|
| S0 | 내부 네트워크·전용 DB 표식·서비스 health | 구성, 버전, 직접 연결, 외부 통신 차단 |
| A | 정상·부분 겹침·다른 자원·취소 후 재사용 | 양쪽 DB 상태·PG 상태·lease 해제 |
| B | 예약 서버 경유와 일정 서버 직접 요청의 슬롯 경쟁 | 각 결과와 최종 활성 구간, 전역 직렬화 여부 |
| C1 | 일정 commit 직후 응답 단절 | 호출 실패와 일정 잔존·PG 상태를 분리 |
| C2 | 일정 성공 뒤 로컬 insert 실패 | 일정 삭제 성공 여부·PG 승인 잔존 |
| C3 | 같은 지점에서 일정 삭제도 실패 | 양쪽 DB 차이·보상 실패 카운터 |
| C4 | 로컬 commit 시점의 지연 제약 위반 | insert 시점 예외와 commit 예외의 보상 범위 차이 |
| C5 | Slack 지연·429 | DB commit과 HTTP 응답 지연·수락/거절·미재시도 |
| D | 제한된 요청으로 DB pool을 점유한 상태에서 별도 조회 | 단계 신호로 점유 확인, 조회 timeout, 해제 후 회복 |

DB 풀 포화는 첫 연결 획득 뒤 제어 신호로 대기시켜 확인한다. 임의 sleep만으로 병목을 주장하지 않는다. 응답 유실은 commit 이후 연결을 닫는 명시적 개입이다. 대규모 RPS·일일 사용자 수·운영 p95를 추정하지 않는다. 이번 smoke의 동시 수·지연·타임아웃은 짧은 합성 조건이며 실제 운영 설정이 아니다.

## 환경·예산·안전

- 2시간 예상 / 3시간 상한. 전용 Compose 프로젝트, 전체 최대 6 CPU·4GiB, 결과 20MiB, 한 시나리오 15초·검증 전체 180초 이내.
- DB/Valkey/PG/Slack 모두 격리 Docker 내부 주소만 사용한다. 실제 회사·운영·dev DB, 실 PG·Slack·클라우드에 연결하지 않는다. 컨테이너에 자격증명·덤프·회사 폴더를 마운트하지 않는다.
- 합성 DB는 tmpfs로 두고 재시작 시 소멸한다. 코드·검증 결과는 호스트에 보존한다. 정리 대상은 이 Compose 프로젝트로 제한한다.
- 필요한 PostgreSQL 드라이버는 기존 실험과 같은 pgx 버전을 사용한다. HTTP·스텁·작은 Valkey 명령은 표준 라이브러리를 우선한다.
- 정상/예상 실패 재현/도구 오류/미실행을 구분한다. 실패 원본을 보존하고 재실행은 별도 세션에 저장한다.

## 완료 조건과 후속 경계

실제 Docker에서 모든 구성요소가 통신하고, 위 최소 사례의 최종 상태와 원본이 재현 가능해야 한다. Go 단위·Race·vet와 기존 웹 회귀를 확인한다. 스텁을 실 PG·Slack 검증으로 표현하지 않는다.

이후에는 증거를 바탕으로 **하나의 변경**(예: 확정 실패의 환불, durable 보상 작업, 결과 조회·멱등 재시도, 풀 점유 범위 축소, 비동기 알림)을 선택해 전후 비교한다. 별도 범위 없이 모든 A/B/C/D 조합·대규모 부하·Outbox·자동 복구 시스템·공개 글을 구현하지 않는다.

## v2 — 핵심 실행 순서와 언어 차이 비교 / 2026-10-23

사용자가 목적을 명확히 했다. 단순히 Go로 실패 응답을 생성하는 도구가 아니라, 두 예약 서버의 핵심 구조를 Go로 다시 작성하고 사례별로 Java/Spring과 비교하며 학습한다. 이 요청으로 아래 로컬 수정·작은 검증을 진행한다. 자동 복구 해법·글·공개 승인은 포함하지 않는다.

v1은 일반 합성 기준선이었다. 당시 코드 15개는 `results/2026-10-23-01/source/`에 environment.json의 SHA와 대조해 보존했다. 당시 raw 결과·분석은 바꾸지 않는다. **v1과 v2는 잠금·스키마·외부 더블이 다르므로 성능 개선 전후로 비교하지 않는다.**

### 이번 범위

1. Go 서비스는 예약 오케스트레이터와 일정 서버 두 개만 구현한다. PG·Slack은 이미 로컬에 있는 digest 고정 Python Docker 이미지와 작은 표준 라이브러리 HTTP 더블로 실행한다. 이들은 제품 서버 구현이나 실제 PG/Slack 공식 에뮬레이터가 아니다. DB·Valkey는 기존 이미지를 유지한다.
2. 결제별 Valkey lease를 제거한다. 생성은 사용자 행 잠금 → 일정 생성 → 로컬 예약·포인트 차감 → 승인 조회 → commit 순서다. 포인트 부족 검사는 원격 생성 뒤에 남겨 늦은 거절과 보상 비용을 관찰한다. 금액·식별자·구간의 입력 검증은 원격 호출 전이다.
3. 취소는 사용자 키 조회 → 사용자 행 → 예약 행 잠금 → 취소 여부 재확인 → 일정 취소 → 로컬 취소·포인트 환급·PG 환불 → commit이다. 중간 로컬 실패 시 원격 취소를 되돌린다. 역보상 실패와 commit 이후 외부 효과의 공백도 숨기지 않는다.
4. 기존 14개 확인과 같은 목적의 회귀 + 같은 사용자 중복 요청·잔액 경쟁·중복 취소·취소 역보상 성공/실패·PG 금액 불일치를 확인한다. HTTP 결과와 별도로 두 DB, 원장, 잔액, 외부 효과 횟수를 판정한다.
5. 비교 자료는 트랜잭션 시작/커밋, 잠금, SQL 실행, HTTP 대기, 보상, commit 뒤 알림 순서로 연결한다. 언어 우열이나 Java 실행 결과를 주장하지 않는다.

### 아직 이식하지 않는 흐름

역콜백·재시도/순서 역전, 일정 변경·완료와 취소의 경쟁, 일부 진입 경로의 겹침 허용 정책, 이용권·기업별 가격·날짜 정책 등은 이번 모델에 포함하지 않는다. 직접 일정 생성은 엄격한 슬롯 보호 경로 하나를 나타내며 모든 관리자 경로를 대표하지 않는다. advisory는 자원 전체를 잠그므로 자원/일 단위 잠금과도 다르다.

자동 환불은 정상 취소에만 있다. 예약 **생성 실패**에 대한 PG 자동 보상·지속 작업·재조정은 아직 없다. 보상 해법을 먼저 넣어 실패가 사라진 상태를 기준선이라고 부르지 않는다.

### 실행·복구

총 예산은 v1의 상한 안에서 유지한다. 기존 실험 컨테이너의 합성 상태는 원본 증거를 확인한 뒤 이 Compose 프로젝트만 재생성한다. 새 스키마 표식은 v2이며 기존 v1 DB에 자동 DDL을 적용하지 않는다. 결과는 새 세션에 저장하고 실행 당시 소스 사본을 함께 둔다. Go test/race/vet/build, Python 단위 검사, Docker 20개 판정, 웹/API 회귀를 수행한다. 실패 시 원본을 보존하고 해당 결함만 고친 뒤 별도 세션으로 재실행한다.

## v3 — 독립 서버 프로젝트와 실제 API 중심 구성 / 2026-10-23

사용자는 역할 분기형 바이너리·테스트 설정 중심 구성이 읽기 어렵고 실제 구조와 다르다고 지적했다. 두 Go 프로젝트, 두 전용 DB·최소 업무 스키마, 1초 지연 PG, 엄격한 초당 1건 Slack 더블, 실제 API를 통한 동시성·보상 검증을 요청했다. 이번 로컬 재구성·검증은 이 지시로 승인됐다. 기존 raw 결과·소스 사본, 다른 랩·웹 기능·미커밋 변경은 보존한다.

- `booking-api/`, `schedule-api/` 각각 별도 Go module·main·net/http 라우트·SQL 스키마·Dockerfile·단위 검사를 둔다. 서로 코드를 import하지 않는다. 도메인별 읽기 쉬운 파일만 나누며 ORM/공통 프레임워크/범용 service-repository 계층은 추가하지 않는다.
- 예약 API는 사용자 잔액·포인트 원장·결제 참조·예약을, 일정 API는 자원·점유·상태 전이·이력을 소유한다. 동일 스키마 복사·role 플래그·제품 API의 `/lab/*`·Fault 헤더·합성 commit guard를 제거한다.
- 생성·취소·직접 일정 진입과 변경/완료/취소 상태 전이·best-effort 역콜백을 구현한다. 앱·관리 화면·가격/기업/이용권 정책은 복제하지 않는다. 엄격한 슬롯 보호 경로만 합성 계약으로 정의한다.
- PG/Slack은 Python 이미지와 별도 작은 스크립트를 쓴다. PG는 경로별 1초 후 성공/실패, 승인 조회·멱등 환불 상태를 제공한다. Slack은 webhook 경로별 엄격한 1초 간격 수락·초과 429/Retry-After, 수락 응답 지연 1초다. 실제 서비스의 모든 정책·내구성을 대체하지 않는다.
- 테스트 준비·최종 DB 조회는 별도 Python 검사기와 psql로 한다. 업무 실패(잔액/금액), 별도 DB 세션의 잠금·롤백, 외부 더블의 실패를 사용한다. 순서 통제가 필요한 DB 개입은 테스트 파일에 두고 제품 스키마·핸들러에 제어 API를 넣지 않는다.
- 로컬 curl과 각 `go run .`이 가능하도록 주소를 환경변수로 받는다. Compose의 공개 포트는 127.0.0.1만 사용하고 컨테이너 네트워크는 internal이다. 원격 origin·회사 DB/덤프/env·실 PG/Slack은 사용하지 않는다.
- 예산: 로컬 3시간 상한, Compose 정상+검사기 합계 6 CPU/4GiB 이내, 결과 20MiB, 개별 HTTP 35초/전체 검사 5분. 100개 동시 webhook과 제한된 100개 예약 실패 burst까지 포함한다. 장시간 D1/D2 부하나 운영 용량 추정은 하지 않는다.
- v1/v2 증거는 유지하고 v3 새 세션을 사용한다. 새 구성 검증 후 이전 역할 분기 소스는 실행 경로에서 제거하며 당시 소스는 결과 폴더에 보존한다. 각 module test/race/vet/build, 더블 단위/통합, 웹/API 검사와 링크·개인정보·draft 보존을 확인한다. 실패·중단은 새 시도 ID로 보존한다. Commit/Push/PR/배포·글 작성은 제외한다.

v3 실행 중 환경 조정: 첫 시도 `2026-10-23-03`은 첫 health 요청에서 연결 거절로 중단됐고 업무 데이터는 쓰지 않았다. 현재 Docker는 internal 네트워크의 PortBindings 요청을 저장하지만 실제 NetworkSettings.Ports를 비워 호스트 포트를 게시하지 않았다. 로컬 curl/별도 go run을 지원하기 위해 전용 일반 bridge + 모든 포트 127.0.0.1 바인딩을 사용한다. 제품 코드의 HTTP/DB 대상은 Docker 서비스명·loopback만 허용한다. **이 변경 후 Docker 네트워크 자체의 외부 egress 차단을 주장하지 않는다.** 주소 allowlist와 더블의 outbound 호출 부재가 실행 범위를 제한한다. 원격 호출·실제 자격증명·회사 데이터는 여전히 사용하지 않는다.

## v4 — Go 서버의 책임·패키지 구조 정리 / 2026-10-24

사용자가 Go의 권장 프로젝트 배치와 net/http·최소 DB 패키지를 기준으로 전체 구조 개선을 요청했다. 이번 범위는 승인된 구조 리팩터링과 회귀 검증이다. 새 연구 질문·복구 해법·DB 정책·API 기능은 추가하지 않는다.

- 각 module에 `cmd/server` 진입점과 `internal/app`, 업무별 `internal/booking` 또는 `internal/schedule`, `internal/httpapi`, `internal/client`를 둔다. 앱은 설정·pool·의존성 조립·수명을, HTTP는 입출력/상태코드만, 업무 service는 트랜잭션·보상·상태 전이를, 같은 업무 패키지의 구체 Store는 SQL을 맡는다. SQL 파일은 `db/`로 이동한다.
- 외부 호출 경계에만 작은 소비자 interface를 사용한다. PostgreSQL Store는 구체 타입이며 범용 repository/UnitOfWork/DI container/ORM을 추가하지 않는다. 양 module은 독립적으로 유지한다.
- 기존 pgx/pgxpool만으로 현재 PostgreSQL 접근을 처리할 수 있어 sqlx를 추가하지 않는다. Go 공식 `cmd`/`internal` 예시는 배치 가이드이며 Spring MVC/JPA와 같은 단일 강제 아키텍처는 아니다.
- API 경로·JSON·상태코드·잠금 순서·tx/HTTP timeout·스키마 내용·PG/Slack 조건은 유지한다. schema/fixture 경로·빌드·실행 명령·Docker mount·문서·테스트를 함께 갱신한다. 오류 분류는 HTTP 패키지에서 상태코드로 변환하고 업무 패키지는 net/http에 의존하지 않는다.
- v3 원본/소스·최종 합성 상태를 보존한 뒤 이 랩만 새 fixture로 준비한다. 21개 실제 API/독립 DB 판정·각 module test/race/vet/build·단독 실행·웹/API 회귀를 실행한다. 구조 변경 결과를 성능 향상으로 해석하지 않는다.
- 검증 실행은 v3와 같은 6 CPU/4GiB 이내·HTTP 35초/전체 5분·100개 로컬 burst 범위, 작업은 3시간 상한이다. 회사 파일·다른 실험·보류 초안·기존 미커밋 변경은 보존한다. 실패 원본은 새 세션에 남긴다. Commit/Push/PR/배포 없음.

## v5 — Go다운 이름·공개 범위·단일 소비자 패키지 정리 / 2026-10-24

사용자는 조사 내용을 바탕으로 불필요한 추상화를 줄이고 단순하고 명확한 Go 코드로 리팩터링하도록 승인했다. API 기능·보상 정책·트랜잭션/잠금/외부 호출 순서·DB 스키마·의존성은 바꾸지 않는다.

- `internal/app`은 실행 파일 하나만 소비하므로 설정·조립·수명을 `cmd/server`의 비공개 함수/파일로 합친다. 실행 명령·환경변수·Docker health 계약은 유지한다.
- 업무별 Service는 유지한다. 생성자가 DB pool을 받아 내부의 비공개 `store`를 구성하며 pool의 종료는 실행 진입점이 맡는다. 외부에서 SQL 저장소를 별도로 조립하게 하던 공개 Store/NewStore를 제거한다. Repository interface·범용 tx wrapper를 도입하지 않는다.
- 작은 외부 호출 interface는 사용하는 Service 옆의 비공개 선언으로 둔다. 모델은 `booking.go`/`appointment.go`, 구체 SQL·DB 오류 변환은 `postgres.go`, 업무 오류는 `errors.go`로 책임을 드러낸다. 독립 두 module의 소량 중복을 공유 라이브러리로 만들지 않는다.
- v4 실행 소스/결과와 최종 합성 DB·PG/Slack 상태를 보존하고 새 fixture에서 같은 21개 통합 판정을 실행한다. Go test/race/vet/build, 기존 웹/API 회귀와 문서 경로·비밀 설정 ignore를 확인한다. 예상 실패 PASS와 자동 복구 완성을 구분한다.
- 실행 예산·로컬 대상·상한은 v4와 같고 새 연구/측정 조건은 추가하지 않는다. 다른 랩·초안·기존 미커밋 변경을 보존한다. Commit/Push/PR/배포는 하지 않는다.

## v6 — Booking API를 요청 흐름별로 읽기 / 2026-10-24

사용자는 service.go의 scheduler/payments/notifier와 요청 검증·모델·여러 테이블 저장 관계를 질문했고, 본인과 다른 독자가 목적을 이해할 수 있도록 파일 분리를 요청했다. 이번에는 질문의 대상인 booking-api의 파일 구성과 읽기 안내만 정리한다. 일정 API·모델/스키마·HTTP 계약·기존 실패/보상 순서·의존성은 유지한다.

- 소비자 interface는 같은 booking 패키지의 dependencies.go에 모은다. 실제 연동 구현은 기존 internal/client에 유지한다. 외부 의존성 계약과 데이터 모델을 구분한다.
- 생성/Create와 저장·승인 확인은 create.go, 취소와 로컬/PG 환불은 cancel.go, 일정 서버 역콜백은 callbacks.go에 둔다. service.go에는 Service 조립·공통 조회/알림을 유지한다. 새 package나 Service/Repository 타입은 만들지 않는다.
- save → saveAndVerifyPayment, refund → cancelAndRefund로 실제 부수 효과를 드러낸다. 함수 본문은 이름을 제외하고 그대로 이동한다. 입력 검증/잠금 이후 검증·SQL 호출·원격 HTTP·로컬 tx/보상의 경계를 실제 코드 순서로 설명한다.
- 현재 Booking은 생성 입력과 조회 응답에 재사용되지만 여러 테이블의 SQL 쓰기는 같은 tx를 받는다. 테이블마다 사용하지 않는 모델이나 같은 필드의 DTO 변환을 추가하지 않는다. 입력/응답 분리가 필요한 조건과 현재 제한은 README에 명시한다.
- v5 결과·소스·합성 최종 상태를 보존하고 동일 21개 로컬 HTTP/DB 회귀, Go test/race/vet/build 및 기존 웹/API 검사를 수행한다. 기존 예산·로컬 범위를 유지한다. 새 장애/성능 측정·복구 해법·이해 완료 선언·Commit/Push/PR/배포는 제외한다.

## v7 — PostgreSQL 책임 분리와 Service의 저장 순서 / 2026-10-24

사용자는 책임별 SQL 파일/메서드 분리를 승인하고, 연관된 로컬 저장이 모두 실행된 뒤 Service가 commit하며 실행 순서를 읽을 수 있게 개선하도록 요청했다. booking-api만 변경한다. 독립 일정 API·스키마·HTTP 계약·금액/보상 정책·로컬 대상·기존 미커밋 변경을 유지한다.

- 같은 booking 패키지 안에서 postgres.go(공통 tx/오류), postgres_booking.go(예약), postgres_user.go(사용자/포인트 원장), postgres_payment.go(결제 참조)로 나눈다. 별도 Repository/interface/UnitOfWork를 추가하지 않는다.
- insertAndDebit/cancelAndCredit를 예약 쓰기와 포인트/원장 쓰기로 나누고 Service에 순서를 드러낸다. 취소/콜백은 예약의 사용자 키 조회 → 사용자 행 잠금 → 예약 행 잠금/재조회 순서를 Service에서 명시한다. 기존 사용자 잠금 helper를 재사용하므로 이 경로는 id 대신 points를 읽되 같은 사용자 행을 FOR UPDATE로 잠근다.
- SQL 저장 메서드는 호출자가 전달한 pgx.Tx만 사용하고 Begin/Commit하지 않는다. Service가 같은 tx로 로컬 쓰기를 마친 뒤 기존 위치에서 한 번 commit한다. 외부 호출·PG 확인/환불·보상/역보상·commit 후 알림 위치는 유지한다. 로컬 tx를 분산 tx로 주장하지 않는다.
- 중간 원장 INSERT 오류가 예약·잔액 변경까지 rollback하는지 실제 PostgreSQL 임시 격리 스키마에서 확인하는 작은 opt-in Go 통합 테스트를 추가하고, 이번 plain/race 검사에서는 명시적 로컬 테스트 URL을 주어 실제 실행한다. 포인트 0 경계와 commit 전 외부 조회 시의 로컬 미공개 상태도 확인한다. 테스트 스키마는 종료 시 제거한다.
- 기존 v6 소스/결과·최종 합성 상태를 보존한 후 같은 21개 API/독립 DB 회귀를 새 세션에서 실행한다. Go test/race/vet/build, Python 더블, 웹/API 검사와 경로/개인정보/ignore 검사를 수행한다. 새 연구 조건이나 복구 해법은 추가하지 않고 v6의 로컬·자원/시간 상한을 따른다. Commit/Push/PR/배포 없음.

## v8 — Schedule API의 업무/저장 파일 정리 / 2026-10-24

사용자가 booking-api를 참고해 다른 Go 서버도 구조를 개선하도록 요청했다. 대상은 독립 schedule-api이며 기존 booking-api 소스·두 서버 계약·스키마·잠금/저장/외부 호출 순서를 보존한다.

- 같은 schedule 패키지·Service/store 타입을 유지한다. service.go는 조립/조회, dependencies.go는 외부 계약, create.go·cancel.go(복원 포함)·complete.go·reschedule.go는 각 업무 순서, callbacks.go는 commit 후 best-effort 전송을 맡는다.
- postgres.go(공통 tx/오류), postgres_appointment.go(일정/이력), postgres_resource.go(자원/UTC 일자 잠금·완료 수)로 나눈다. insert/lock/event 등 모호한 private 이름만 역할에 맞게 바꾸며 SQL·함수 본문은 이름 외 그대로 이동한다. Begin/Commit은 기존 Service 경계에서 유지한다.
- 새 Repository/interface/공통 라이브러리·기능·장애 주입·스키마/정책은 추가하지 않는다. 일정 상태와 이력은 하나의 책임으로 묶어 테이블마다 파일을 기계적으로 만들지 않는다.
- 기존 Go 검사(booking의 실제 DB 임시 스키마 검사 포함), Race/vet/build, 기존 21개 두 서버 HTTP/독립 DB 회귀와 웹/API/Python 검사를 수행한다. 순수 이동은 원본 함수/SQL 비교로도 확인하고 같은 검증을 위한 새 테스트 코드를 복제하지 않는다.
- v7 최종 합성 상태와 원본/소스를 보존한 후 이 랩만 새 fixture로 실행한다. 기존 로컬 예산·상한을 따른다. 회사/운영 자원·다른 랩·보류 초안·기존 미커밋 변경은 보존한다. Commit/Push/PR/배포 없음.
