## Original Question — 공개용 요약

회사에서 발생한 동시성 문제와 비슷한 상황을 독립 실험에서 단계별로 재현하고 이해한다.

배경은 사용자가 제공한 경험이다. 아래 모델·시간·상한은 독립 실험을 위해 정한 합성 조건이며 실제 업무 규칙·측정값이 아니다. 공개 문서에는 질문의 사적인 맥락 대신 이 요약을 남긴다. 독립 실험의 결과와 실제 업무 환경의 원인 검증은 구분한다.

## Research Question

**같은 자원의 겹치는 시간 구간을 두 트랜잭션이 동시에 등록할 때, 먼저 조회한 뒤 저장하는 방식은 어떤 순서에서 무결성을 잃는가? 자원 행 잠금 하나를 추가하면 그 순서와 최종 상태는 어떻게 달라지는가?**

첫 연구에서는 하나의 DB 안의 경쟁만 다룬다. HTTP 서버, 서비스 간 통신, 과금·잔액, 인증·테넌트, 사용자별 중복 제한, 운영 데이터 이전은 구현하지 않는다. 이 주제는 기존 Go Load Lab의 처리량 연구와 독립적이다.

## Background

검증 축은 시간 구간의 충돌, 잠금의 보호 범위, 중복 처리, 트랜잭션과 외부 부작용의 경계다. 안전하지 않은 기준 구현은 원인을 관찰하기 위해 **의도적으로 만드는 합성 구현**이다.

DB 잠금·격리 수준의 효과를 묻기 때문에 Mock만으로는 답할 수 없다. 별도 로컬 PostgreSQL과 독립 연결을 사용하는 작은 Go 테스트로 검증한다. 특정 애플리케이션 프레임워크의 프록시·flush·commit 동작까지 검증했다고 주장하지 않는다.

## Hypotheses

실행 전 예상이며 아직 검증하지 않았다.

1. H1: 충돌 행이 없는 상태에서 두 트랜잭션 모두 조회를 끝낸 뒤 쓰게 하면, 보호 없는 구현은 겹치는 두 행을 모두 커밋할 수 있다. 둘 다 커밋하지 못하면 예외·격리 수준·제약·제어 순서를 확인하고 미재현으로 기록한다.
2. H2: 항상 존재하는 동일 자원 행을 먼저 잠그고 조회·삽입·커밋까지 유지하면, 뒤의 트랜잭션은 앞의 커밋을 확인하고 충돌을 거절할 것으로 예상한다. 겹치는 두 행이 커밋되면 반증이다.
3. H3: 이 잠금은 같은 자원에 한정된다. 인접 구간과 서로 다른 자원까지 모두 거절하거나 전역 직렬화하면 올바른 해결로 보지 않는다.

## Method

### 합성 모델과 불변 조건

- 자원 `R1`, `R2`와 임의 요청 식별자를 사용한다. 등록 구간은 UTC 시작·종료 시각으로 표현하고 `start < end`를 요구한다.
- 동일 자원에서 커밋된 활성 구간 두 개가 겹치면 안 된다. 겹침 판정은 `a.start < b.end AND b.start < a.end`이다. `[start, end)`로 정의하여 끝과 시작이 맞닿은 구간은 허용한다. 이는 실험에서 정한 계약이다.
- P1의 기본 충돌 입력은 `R1 [13:00, 13:30)`과 `R1 [13:15, 13:45)`이며 같은 합성 날짜를 사용한다. 시작 시각만 비교하는 오류를 피한다. 정확히 같은 구간도 별도 확인한다.
- 트랜잭션 내부 미커밋 상태는 외부 판정 대상과 구분한다. 모든 참여 트랜잭션의 commit/rollback 완료 후 별도 연결에서 최종 상태를 읽는다.
- 충돌 쌍 개수, 활성 행 수, 실제 남은 구간, 각 트랜잭션의 결과를 함께 확인한다. 성공 응답·에러·타임아웃만으로 무결성을 판단하지 않는다.

### 단계와 완료 조건

아래는 **미실행 계획**이다. 단계별 완료 여부는 실행 후 증거와 함께 기록한다. 한 단계가 실패하면 전체를 재시작하지 않고 원인과 남은 단위를 먼저 확인한다.

| 단계 | 목적과 수행 작업 | 완료 조건·증거 | 실패 시 처리 |
|---|---|---|---|
| P0 — 격리 환경과 판정기 | 독립 Go 모듈·전용 로컬 PostgreSQL, 최소 합성 fixture와 최종 상태 조회. DB 연결 두 개와 별도 관측 연결을 확보한다. 충돌·인접·다른 자원·잘못된 구간의 순차 테스트부터 작성한다. | 버전·이미지 식별자·격리 수준·pool 설정·정확한 명령 보존. 서로 다른 DB 세션임을 확인한다. 판정기가 합성 충돌 상태는 탐지하고 정상 상태는 허용한다. | 대상 DB가 전용인지 확인할 수 없거나 참여 연결을 확보하지 못하면 중단한다. 임의 DB를 초기화하지 않는다. |
| P1 — 의도한 실패 재현 | 보호 없는 조회→삽입 경로에서 두 연결이 모두 충돌 없음 조회를 마친 뒤 쓰도록 barrier를 둔다. | 두 조회·두 commit·최종 충돌 상태를 연결한 로그. 동일 조건 3회 각각 판정. 무결성 위반을 예상한 특성화 테스트로 보존한다. | barrier timeout·접속 실패·중단은 의도한 실패와 구분한다. 두 행이 커밋되지 않으면 미재현이며 해결 단계의 성공 근거로 쓰지 않는다. |
| P2 — 한 가지 보호와 회귀 | 미리 존재하는 자원 행에 트랜잭션 범위 `SELECT … FOR UPDATE`를 추가한다. 잠금 뒤 충돌을 조회한다. 다른 해결책·격리 수준·스키마 보호를 동시에 바꾸지 않는다. | 같은 초기 데이터·입력·격리 수준에서 한 건 commit, 다른 한 건 충돌 거절, 최종 겹침 0. 아래 반례·rollback 검증 통과. 변경 전후 코드 식별자·증거 연결. | 실패 원본을 보존한다. DB 제약·재시도 등을 추가해 결과를 맞추지 않는다. 다른 해결책은 새 범위를 정한 뒤 비교한다. |

### 실행 순서의 통제

- P1은 두 트랜잭션의 **조회 완료 후** 합류시킨다. 두 연결이 실제 경쟁했는지 DB 세션 ID와 단계 신호를 남긴다. 임의 sleep·높은 Worker 수만으로 결정적 재현이라고 부르지 않는다.
- P2에서는 첫 트랜잭션이 자원 잠금을 획득한 뒤 두 번째가 같은 잠금을 시도하도록 신호를 둔다. 첫 트랜잭션을 유지한 채 별도 관측 연결로 두 번째의 잠금 대기를 확인한 뒤 첫 commit을 허용한다. 관측도 제한 시간 안에 끝나야 한다.
- **배타 잠금 획득 뒤 양쪽이 모두 barrier에 도착하기를 기다리지 않는다.** 두 번째가 도착할 수 없어 테스트 자체가 멈춘다. pool 크기 부족으로 경쟁을 없애서도 안 된다.
- 잠금 때문에 P1의 강제 interleaving이 P2에서 성립하지 않는 것은 비교의 핵심이다. 같은 입력·초기 상태를 사용하되 제어 지점의 차이를 기록한다. 모든 실행 순서가 같았다고 주장하지 않는다.
- PostgreSQL Read Committed를 제안한다. 실제 설정을 기록하고 모든 비교에서 유지한다. 더 강한 격리 수준이나 자동 재시도는 이 비교에서 도입하지 않는다.

### 최소 실패·회귀 표

| 사례 | 통제·개입 | 예상 결과와 최종 상태 |
|---|---|---|
| 같은 자원·동일/부분 겹침 | P1 조회 후 합류 / P2 잠금 경쟁 | P1은 두 commit과 충돌을 관찰. P2는 하나만 남고 충돌 0. |
| 같은 자원·인접 구간 | 경계가 같은 입력으로 순차 및 동시 시도 | 두 건 commit, 충돌 0. P2에서는 잠시 직렬화될 수 있음. |
| 다른 자원·같은 구간 | R1 잠금 유지 중 R2 진행 | R1 해제 신호 전에 R2 완료. 전역 잠금이 아님을 사건 순서로 확인. |
| 첫 트랜잭션 rollback | 잠금 획득·삽입 후 의도적 예외, 두 번째 대기 | 첫 데이터 없음, 잠금 해제 후 두 번째 commit, 잔여 트랜잭션 없음. |
| 보호 우회 | 시험용 직접 SQL 경로로 한 건씩 겹치게 삽입 | DB 제약이 없는 P2에서는 위반 가능함을 확인·기록. 적용 경로의 보호를 DB 전체 보장으로 확대하지 않음. |
| 제어 실패 | barrier·lock 관측의 제한 시간 초과 | 미재현/실험 도구 오류로 기록. 무결성 위반 또는 해결 성공으로 집계하지 않음. |

우회 테스트가 보여주는 한계는 이번 단일 변경의 범위다. 우회까지 차단해야 한다면 DB 제약을 별도 비교하는 후속 연구가 필요하다. 이 단계에서 몰래 추가하지 않는다.

## Variables / Metrics

- 독립변수: 조회·쓰기 경로의 자원 행 잠금 유무. 초기 데이터·입력·DB 버전·격리 수준·참여 트랜잭션 수 2는 유지한다.
- 지표: 각 연결의 조회·잠금 시도/획득·commit/rollback 사건, SQLSTATE·오류 종류, 최종 행 수·구간·충돌 쌍 수, 정리 후 잔여 세션/잠금. 시간은 원인 판정 보조이며 처리량 비교는 하지 않는다.
- 주요 충돌 비교는 조건별 3회, 회귀는 사례별 1회 이상을 제안한다. 유효/미재현/도구 오류/중단을 분리한다. 실패율을 제품의 운영 발생 확률로 해석하지 않는다.
- warm-up·RPS·분위수는 성능 연구가 아니므로 적용하지 않는다. 반복마다 새 fixture로 시작하고 트랜잭션 종료·잠금 해제를 확인한다.

## Environment / Budget

- 제안 환경: 로컬 Go + 별도 PostgreSQL 컨테이너 한 개. 기존 웹/API, D1, 운영·회사 DB, 외부 서비스에 연결하지 않는다. 새 Go 의존성은 필요한 DB 드라이버 하나를 우선 검토한다.
- 아직 확인하지 않은 항목: 사용 가능한 Go·컨테이너 런타임·PostgreSQL 버전, 이미지·드라이버 버전. P0에서 가용성을 확인하고 버전/이미지 digest를 고정한 뒤 비교한다. 설치·다운로드 필요 시 그 사실을 기록한다.
- 제안 한도: P0–P2 구현·검증 예상 2시간, 최대 3시간. DB 1개·참여 연결 2개와 관측 연결 최소 1개, 컨테이너 최대 2 CPU / 1GiB, 산출물 50MiB 이내. 초과 전 중단·현황 보고.
- 시나리오 전체 15초, 개별 DB 문장 최대 5초의 상한을 제안한다. 관측용 context와 DB timeout을 함께 사용한다. timeout 발생 시 원인과 DB 최종 상태를 별도 확인하며 성공으로 처리하지 않는다.
- 위 값은 승인할 실행 예산의 제안이며 실제 실행 환경·측정 결과가 아니다. 가용성이 다르면 무단 변경 대신 계획 변경을 남긴다.

## Risks / Limitations

- 연결 URL은 로컬 전용이어도 기존 DB를 가리킬 수 있다. 명시적으로 생성·확인한 실험 DB만 허용하고 원격 호스트·알 수 없는 기존 DB에서는 즉시 중단한다. 자동으로 사용자 DB를 drop하지 않는다.
- 합성 데이터·독립 SQL만 새로 설계한다. 비밀 설정·연락처·업무별 예외는 fixture에 넣지 않는다.
- P2 자원 잠금은 같은 규약을 따르는 경로만 보호한다. DB 제약의 대체, 모든 진입점의 안전, 분산 원자성, 특정 프레임워크의 동작을 증명하지 않는다.
- 이 실험의 결과로 실제 업무 환경의 장애 원인을 확정할 수 없다. 운영 시스템의 실제 제약·데이터·배포 구성은 검증 범위 밖이다.
- 결정적으로 통제한 일부 순서와 소수 반복이 모든 실행 순서의 안전성 증명은 아니다. Go Race Detector도 DB 무결성 검증을 대신하지 않는다.

## Acceptance Criteria

1. P0의 격리·연결·판정기 검증을 먼저 통과한다.
2. P1은 의도한 실패의 실제 DB 상태를 보존한다. 미재현을 통과로 바꾸지 않는다.
3. P2는 수정 하나와 동일 입력·초기 상태를 연결하고 충돌·허용·rollback·우회의 결과를 모두 설명한다. 가설이 맞지 않아도 정확한 증거와 한계가 있으면 연구 결과로 인정한다.
4. 향후 작성할 최소 테스트 명령은 실험 디렉터리에서 `go test -count=1 -timeout=90s ./...`, `go test -race -count=1 -timeout=90s ./...`, `go vet ./...`이다. **현재 Go 모듈이나 테스트는 없으므로 이 명령은 아직 실행할 수 없다.** DB 준비·정리 명령은 P0의 실제 구성과 함께 확정한다.
5. 실행 명령·버전·코드 hash·시나리오별 원본·최종 상태가 재개 가능한 형태로 연결된다. 이해 대화·사용자 설명·글 작성 여부는 테스트 통과와 분리한다.

## 보존·재개 계획

승인 후 이 디렉터리 안에 최소 코드와 재현 README, 필요 시 `RESEARCH-RECORD.md`를 작성한다. 원본은 `results/<session>/<stage>-<case>-<attempt>/`처럼 시도별로 분리하고 단계 로그·오류·DB 최종 조회·완료 상태를 저장한다. 이는 경로 제안이며 현재 결과 파일은 없다.

실패·중단 원본을 덮어쓰지 않는다. 재개 시 유효 완료만 건너뛰고 누락·손상·미재현은 구분한다. 정리 전 증거를 보존한 뒤 해당 시도 fixture와 소유한 컨테이너만 정리한다. 별도 ExecPlan 시스템이나 범용 Failure Matrix 실행기는 만들지 않는다.
