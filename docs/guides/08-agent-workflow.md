# 에이전트 작업과 검증

이 문서는 기존 [AGENTS](../../AGENTS.md)의 작업별 진입점이다. 연구 계획·승인·재개는 [Lab Workflow](14-engineering-lab-workflow.md)가 소유한다. 스킬 설치는 원격 작업이나 새 기능의 승인이 아니다.

## 필요한 절차 선택

| 작업 | 사용할 기준·스킬 | 완료 증거 |
| --- | --- | --- |
| 문서·AGENTS·SKILL 수정 | `writing-for-agents`: 짧은 진입점과 조건부 원본 링크, 관찰 가능한 완료 조건 | 링크 검사·하네스 테스트·diff; 실제 명령과 계획 구분 |
| 원인 불명의 버그·회귀 | `diagnosing-bugs`: 실제 증상을 판정하는 재현부터 확보 | 최소 재현, 수정 전 실패와 수정 후 성공; 재현 불가이면 정확한 경계 |
| API·형식·공유 상태 변경 | `blast-radius`: 직접 호출자 밖의 소비자와 핵심 가정 확인 | 실제 코드·부수효과·호환성 검사 |
| 명확한 버그 회귀 테스트 | pstack `tdd` 또는 기존 프로젝트 테스트 관례 | 실패 이유를 먼저 확인하고 최소 수정 후 재실행 |
| PR·WIP 리뷰 | 요구사항 충족과 저장소 규칙 준수를 별도로 확인 | 기준 ref와 staged·unstaged·새 파일의 포함 범위 |
| 성능 수치 보고 | `benchmark-checklist`와 기존 Lab 계약 | 오류·실제 작업·반복 횟수·변동 범위·병목 |
| 보안 질문·부분 검토 | `security-audit` guidance mode | 낮은 권한 주체 → 입력 → 보호 경계 → 피해와 근거 |
| 코드베이스 보안 감사 | `security-audit` full audit mode | 범위·profile·coverage ledger·독립 검증·형식 검사·잔여 검증 |

위 스킬은 선택적 도구다. 없는 스킬의 성공을 주장하거나 설치를 자동으로 시작하지 않는다. 명시 호출 전용인 스킬의 정책을 이 안내로 바꾸지 않는다. 같은 이름의 TDD는 소속 플러그인을 구분하고, 기존 승인과 저장소의 테스트 경계를 우선한다. API 무결성이 계약이면 HTTP 응답뿐 아니라 최종 DB 상태·롤백·중복 방지를 확인할 수 있다.

기본은 현재 코드의 가장 작은 완결 변경이다. 복잡한 설계를 비교할 때만 architect/arena를 선택하고, 모든 수정에 전체 poteto-mode와 다른 전체 절차를 겹치지 않는다. 스킬 설명만으로 실제 모델 다양성·권한 격리·훅 실행을 단정하지 않는다.

## 변경 영역별 검증 경계

실제 명령의 원본은 앱의 package.json, 각 Lab README와 [품질 문서](06-quality-and-safety.md)다. root 통합 npm 스크립트를 가정하지 않는다.

| 변경 | 우선 실행·확인 | 그 결과로 주장할 수 없는 것 |
| --- | --- | --- |
| Entry·Guide·하네스 | `scripts/check_docs.py`, `scripts/test_check_docs.py`, diff 검사 | 앱 동작·외부 URL·문서 앵커의 정상 여부 |
| Web·Markdown | 기존 Web QA와 `content:check`, 영향받는 렌더링·draft 제외 경로 | 초기 HTML의 글별 SSG, 실제 기기·배포 확인 |
| 방문 집계 API | API QA·로컬 합성 D1 테스트, 동의·Origin·중복·자정·롤백 | 운영 D1 데이터·CF 헤더 출처·실제 Access 정책 |
| Lab | 해당 실험의 테스트와 합성 데이터, 기존 계획·결과 계약 | 운영 분산 시스템 전체의 안전성 |

Web의 `posts.test.mjs`는 임시 복사본에서 합성 글을 만들고 실제 Vite 파이프라인을 확인한다. `localization.test.mjs`와 `visits.test.mjs`는 Vite middleware와 합성 브라우저 상태를 사용한다. 브라우저·모바일 기기 E2E와 구분한다. API 테스트는 로컬 D1/workerd를 실행하므로 단순 파일 검사로 취급하지 않는다.

## 보안 감사 실행 계약

전체 감사의 원본은 설치된 security-audit 스킬이다. 이 문서에 공격 유형·스키마·검증 절차를 복제하지 않는다. 대상 커밋, 미커밋 변경, 범위, profile, 예산을 고정하고 과거 기록과 현재 증거를 분리한다. 공개 Web/API·CI와 로컬 Lab은 서로 다른 신뢰 경계다. 제외한 영역은 안전하다고 표현하지 않는다.

- 대상 코드는 읽기 전용이다. 수정 권고는 감사 결과로 남기고 실제 보안 수정은 별도 구현 범위에서 진행한다.
- 빌드·테스트·PoC는 외부 네트워크 차단, 비밀정보 없는 허용 환경, 읽기 전용 소스·도구, scratch 전용 쓰기와 자원·시간 제한을 모두 갖춘 OS 격리에서만 실행한다. 컨테이너 이름이나 `--offline`만으로 충족했다고 보지 않는다.
- 실행 환경이 부족하면 소스 분석은 계속하고 필요한 실행을 미검증으로 남긴다. 샌드박스를 벗어나 대상 코드를 실행해 우회하지 않는다. 기록 형식·coverage 검증기의 통과는 취약점 진실성을 증명하지 않는다.
- 운영 엔드포인트, 원격 D1/R2, Cloudflare/GitHub 제어면, 실제 사용자 데이터는 이 로컬 감사의 실행 대상이 아니다. 실제 정책이 결정적이면 `needs_validation`과 소유자 확인 계획을 남긴다.
- 전체 결과와 로그는 대상 저장소 밖의 이번 작업 전용 디렉터리에 둔다. ignored `docs/private/`, Lab 결과, 원본 이력서·자격증명은 기본 감사 입력에 넣지 않는다. 기록에 로컬 절대 경로나 기존 공개 연락처를 불필요하게 복제하지 않는다.
- `confirmed`만 심각도를 부여하고 `needs_validation`·`rejected`를 구분한다. 개선 권고와 실제 경계 위반을 섞지 않는다. 발견자와 검증자는 분리한다.

## 기록과 종료

보고에는 변경 파일, 실제 실행 명령·결과, 확인하지 못한 경계와 우선 개선 방향을 남긴다. 기존 계획·Research Record·Archive가 소유한 기록을 다른 형식으로 중복 작성하지 않는다. 반복된 실패는 문장 추가보다 실행 가능한 검사로 예방하고 그 검사가 실제 실패를 잡는지 확인한다.

새 배포·리소스·공개 범위 변경은 AGENTS의 사용자 승인 경계를 따른다. 과거의 로컬 이전 계획을 현재 상태로 실행하거나, 한 번의 소스 감사로 운영 안전성을 선언하지 않는다.
