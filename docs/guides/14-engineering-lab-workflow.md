# Engineering Lab Workflow

이 문서는 Codex가 연구를 보조할 때 따르는 절차다. 별도 Agent 서비스나 범용 Runner는 없다. 운영 철학은 [05](05-lab-practices.md), 콘텐츠 계약은 [03](03-content-and-writing.md), 안전·검사 명령은 [06](06-quality-and-safety.md)가 원본이다.

## 진입과 승인 경계

| 단계 | 산출물 | 다음 단계 조건 |
|---|---|---|
| A — Research Planning | 질문·가설·검증 계획 | 기본은 여기서 멈춤. 사용자가 범위·예산을 승인하면 B |
| B — Implementation & Execution | 필요한 코드/자료 조사·테스트·실행 기록 | 승인 범위 안에서 C로 진행 |
| C — Evidence & Analysis | 원본 검증·계산·해석·한계 | 근거가 부족하면 부분 완료로 보고. 예산 밖 추가 측정 금지 |
| D — Follow-up Questions | 후속 질문 후보·빈 사용자 회고 | 새 질문은 선택/승인 후 별도 A. 자동 실행 금지 |
| E — Lab Draft | 요청받은 Markdown 초안 | 충분한 근거 + 초안 작성 요청. 공개는 별도 승인 |

사용자가 계획과 실행을 함께 명시적으로 승인한 경우 그 지시와 범위를 계획에 연결하고 중복 승인을 요구하지 않는다. 승인은 다른 대상·확장한 조건·추가 예산에 자동 적용되지 않는다. “계획만” 요청에서는 실험 코드·측정·새 연구 조사를 시작하지 않는다. A에 필요한 기존 자료의 읽기 전용 확인은 가능하다. 후속 후보를 승인한 경우에도 실행 범위가 불명확하면 먼저 A를 구체화한다.

실제 허용 범위는 현재 사용자 지시를 기준으로 판단한다. Harness 구축 자체는 새 연구 실행·새 글 작성·공개 승인이 아니다. 기존 Phase 4의 완료 상태와 당시 승인 근거를 소급 변경하지 않는다.

## A — Research Planning

[계획 템플릿](../../templates/research-plan.md)을 복사해 보통 `labs/<slug>/PLAN.md`에 둔다. 계획만 있는 디렉터리도 허용한다. 간단한 이론 질문은 하나의 연구 노트 안에 같은 필드를 두어도 된다. 민감한 내용은 저장소 밖에서 관리한다.

- **Original Question:** 사용자의 질문을 원문 그대로 보존한다. AI의 재구성과 혼동하지 않는다.
- **Research Question / Background:** 답할 범위와 관련 개념, 제외할 질문을 좁힌다. 코드가 필요한지 먼저 판단한다.
- **Hypotheses:** 결과를 보기 전의 예상과 반증 가능한 조건, 작성 시점을 기록한다. 개방형 문헌 탐구에서 사전 가설이 없으면 그 이유를 쓴다.
- **Method / Variables / Metrics:** 방법, 독립·종속변수·통제조건, 단위·분모·표본·실패 정의·계산 방식을 정한다. 이론/코드 검토에서 해당하지 않는 항목은 이유와 함께 해당 없음으로 둔다.
- **Environment / Budget / Risks:** 버전·실행 위치·대상 권한, 전체 예상 시간과 상한·자원 한도·중단 조건, 데이터 보존·공개 위험을 정한다. 허가된 대상도 환경별 제한을 따른다.
- **Acceptance Criteria / Limitations:** 예상 결과와 무관하게 완료를 평가할 기준, 설계로 답할 수 없는 범위를 쓴다. “RPS가 높게 나옴”을 성공 기준으로 삼지 않는다.

계획 버전·승인 상태·승인한 사용자 지시/시점·허용 단계·조건·예산·초안 여부를 남긴다. 기본 상태는 **승인 대기**다. 가설 수정은 원문을 보존하고 변경 시점·이유·이미 본 결과를 별도 이력으로 남긴다. 범위나 실행 조건 변경은 영향과 새 계획을 제시하고 필요한 승인 전 멈춘다.

## B — Implementation & Execution

1. 승인과 브랜치/미커밋 상태를 확인한다. 작은 독립 재현부터 만들고 표준 라이브러리·기존 도구를 우선한다. 이론 연구라면 코드 대신 승인된 자료 조사/분석만 한다.
2. 중요한 로직·입력 경계·집계·실패 경로를 테스트하고 환경·버전을 확인한다. 실제 측정 전에 검사 결과를 남긴다. 실패한 검사를 숨기거나 비활성화하지 않는다.
3. 실행 전 코드/설정 식별자(커밋과 미커밋 diff 또는 파일 hash), 정확한 명령·cwd·비밀을 제외한 환경변수, 실행 시각·도구 버전·입력·조건을 기록한다. 웹과 실험은 직접 의존하지 않는다.
4. 계획의 warm-up·반복·순서·휴식·종료/취소·timeout을 지킨다. 승인된 시간/CPU/메모리/저장량 한도에 도달하기 전에 신규 작업을 멈추고 진행 중 작업을 안전하게 종료한다. 외부 서비스 권한이 불분명하면 부하를 보내지 않는다.
5. 결과가 예상과 달라도 코드/조건/수치를 맞추지 않는다. 측정 결함을 발견하면 실패 원본과 이유를 보존하고 수정 전후를 다른 세션으로 분리한다. 승인 밖 재측정은 요청한다.

## 중단·재개 — B/C 공통

짧은 문헌 노트는 Markdown 상태 표로 충분하다. 장시간 반복에는 실험별 작은 checkpoint/스크립트를 선택할 수 있다. 공통 JSON 스키마나 Runner를 강제하지 않는다.

- 단위 ID(조건·반복·세션), 상태, 산출물, 명령/환경 식별자, 오류·다음 행동을 기록한다. 최소한 **대기 / 실행 중 / 유효 완료 / 실패·중단 / 손상**을 구분한다.
- 완료는 프로세스 종료나 파일 존재만으로 판단하지 않는다. 크기·파싱·필수 조건·집계 불변식·중단 여부를 검증하고 원본과 근거를 연결한다. checkpoint와 파일이 충돌하면 재검증하고 이유를 기록한다.
- 가능한 경우 배타적 임시 파일에 저장 → flush/fsync → 내용 검증 → 원자적 교체 → 완료 상태 확정 순서를 쓴다. 미완료 임시 파일·stderr는 지우지 않고 별도 시도 ID로 보존한다. 완료 상태 기록 직전 중단됐다면 유효 파일을 복구 근거로 삼고 중복 실행하지 않는다.
- 재개 전에 유효 결과 목록과 hash/조건을 확인한다. 이미 유효한 단위는 건너뛰고 실패·손상·누락만 승인 범위에서 다시 수행한다. 기존 파일을 덮어쓰거나 빈 파일을 0 성능으로 집계하지 않는다.
- 코드·설정·환경이 달라졌으면 별도 세션/디렉터리에 기록한다. 비교/합산 여부와 한계를 설명한다. 모든 실행을 중단된 세션과 동일했다고 주장하지 않는다.
- 중간 보고에는 예정/유효/실패·중단/손상/남은 수, 원본 경로, 사용 예산, 안전하게 재개할 다음 단위를 남긴다. 계획 수와 유효 완료 수는 별도로 계산한다.

## C — Evidence & Analysis

[연구 기록 템플릿](../../templates/research-record.md)에 계획·원본·계산 경로를 연결한다. 실험 데이터 보고서는 `labs/<slug>/`에 보존하고 글의 문체와 분리한다.

| 분류 | 기록할 것 |
|---|---|
| **Observed** | 실제 관측·측정·소스/문서에서 확인한 사실. 원본/조건/위치와 실패·이상 결과 포함 |
| **Calculated** | 원본에서 유도한 값. 입력 파일, 식/스크립트 버전, 단위·분모·표본 수·제외 기준과 생성물 |
| **Interpretation** | 관측을 설명하는 이론적 해석. 근거 자료와 다른 가능한 설명, 적용 범위 |
| **Unverified** | 미측정·재현되지 않은 가설과 부족한 증거. 무엇을 확인해야 답할 수 있는지 |

원본을 검증한 뒤 계산하고 그래프는 계산한 자료에 연결한다. 표본 수·반복 최소/최대/편차·집계 정의·환경 차이를 드러낸다. 상관관계를 원인으로 바꾸지 않고 불안정한 결과도 남긴다. 기존 분석 스크립트가 산출물을 덮어쓰는지 확인한 후에만 실행한다.

기술 설명은 공식 문서·표준·해당 버전의 소스를 우선하며 URL과 **버전 또는 실제 확인일**, 관련 절/파일을 기록한다. 문서를 읽었다는 기록과 실험으로 입증한 사실을 구분한다. 직접 확인하지 않은 출처에 확인일을 만들어 넣지 않는다. 부족한 증거는 성공으로 처리하지 않는다.

## D — Follow-up Questions

후속 후보는 가능한 2–4개만 제시한다. 각 후보에 질문, 기존 근거와 연결, 검증 가치, 방법, 추가 비용/복잡도, 우선순위를 적는다. 결과가 충분하면 더 만들지 않아도 된다. 선택되지 않은 후보는 **미승인·미실행**으로 남긴다.

사용자 전용 회고인 **“이번 연구를 통해 이해한 내용”**, **“아직 이해하지 못했거나 납득하지 못한 내용”**은 실제 의견이 없으면 빈칸으로 남긴다. AI의 개념 요약은 C의 해석에 두고 사용자의 이해를 대신 선언하지 않는다.

## E — Lab Draft

충분한 근거가 있고 초안 작성 요청이 있으면 [실험 글](../../templates/experiment.md) 또는 [학습 노트](../../templates/lab-note.md)를 재사용한다. A에서 초안까지 명시적으로 승인받았다면 다시 승인받을 필요는 없다.

- [콘텐츠 스키마](03-content-and-writing.md)에 맞춰 `content/lab/<slug>.md`, **draft: true**로 작성한다.
- 실제 질문 → 사전 예상 → 방법 → 근거/계산 → 해석/실패 → 한계 → 마지막 후속 후보 흐름을 사용한다. 사용자 경험·동기·의견은 제공된 것만 쓴다.
- 코드·계획·원본·보고서·그래프·공식 출처를 연결한다. 아직 원격에 없는 커밋 링크를 만들지 않는다. 공개 전에 실제 경로와 공개 가능한 데이터 범위를 검토한다.
- content:check·초안 공개 번들 제외와 변경 범위 검사를 실행한다. 초안 화면은 격리 미리보기에서만 확인한다. [03의 절차](03-content-and-writing.md#첫-글의-로컬-확인-순서)를 따른다.
- 공개 승인 전 draft를 false로 바꾸지 않는다. Push/PR/배포도 별도 권한이다. Public Git의 draft는 비공개가 아니므로 민감한 자료를 넣지 않는다.

## 사용 예시와 적용 근거

사용자는 “`[질문]`을 Lab Workflow Stage A로 계획해 줘. 실행은 승인 후 진행해.”라고 시작할 수 있다. 승인할 때는 계획 버전·대상·조건·예산·허용 단계(초안 포함 여부)를 지정한다. 재개 요청에는 계획/기록 경로와 남은 범위를 전달한다. AI는 기존 유효 산출물을 먼저 검증한다.

[Harness 검토 기록](../archive/work-records/15-engineering-lab-harness-review-2026-10-15.md)에 기존 Go 실험의 읽기 전용 대응 관계와 **계획만 작성한 가상 사례**를 둔다. 이 절차는 문서 기반 작업 계약이며 별도 실행 권한을 기술적으로 강제하는 서비스는 아니다.
